# save_perf: фриз при сохранении мира

## Стенд

Сценарий `save_perf` (`SentisTests/Scenarios/SavePerfScenario.cs`):

- спавн тех же 64 копий `Refinery_test`, что в `refinery_perf` (32 064 блока), в 12 км от игроков, 15 с на затухание;
- **профиль выделений** одного грида: `GetObjectBuilder` целиком, по типам блоков, отдельно компоненты, инвентари и системы грида
  (вызываются те же ванильные методы по отдельности, без патчей);
- **детализация выделений** для одного конвейера, одного завода и конвейерных линий: голый объект билдера, контейнер
  компонентов, каждый компонент отдельно;
- **проверка сериализации компонентов:** `Components.Serialize()` каждого блока (с патчем SentisOptimisations)
  сравнивается по XML с дословной копией ванильной реализации (пустой контейнер приравнивается к `null`:
  `ShouldSerializeComponentContainer` его не пишет);
- **проверка параллельного снимка:** 3 раунда; object builder всех тестовых гридов собираются последовательно дважды и параллельно один раз,
  XML сравнивается побайтно;
- **два сохранения** через `ITorchBase.Save()` (тот же путь, что `!save`) с паузой 10 с. Окно замера - от запроса до конца записи плюс 5 с.

Мир сохраняется вместе с тестовыми гридами; они пропадут из сейва при следующем сохранении после очистки.

Запуск: `POST /test` `{"name":"save_perf"}`, ~75 секунд.

## Как устроено сохранение

`TorchAsyncSaving` вызывает в игровом потоке `MySession.Save`: чекпоинт, `GetSector` → `MyEntities.Save`
(`BeforeSave` и `GetObjectBuilder` каждой сущности), данные воксельных карт, компоненты сессии.
Потом `MySessionSnapshot.SaveParallel` сериализует XML и пишет на диск в фоне; кадры в это время не страдают.

dotTrace (два сохранения, игровой поток): `MyCubeGrid.GetObjectBuilder` - 234 мс из 243 мс снимка,
из них `MyComponentContainer.Serialize` 156 мс, сборки мусора 79 мс. Чекпоинт и воксели - меньше 10 мс.

## Что сделано (SentisOptimisations)

1. **`ParallelEntitySave`** заменяет `MyEntities.Save`: object builder гридов собираются через `Parallel.For`, пока игровой поток ждёт.
   Временная коллекция в `MyComponentContainer.Serialize` помечена `[ThreadStatic]`, так что ванильный код к этому готов.
2. **`ComponentContainerSerialize`** заменяет `MyComponentContainer.Serialize`: нет временного списка на каждый тип компонента,
   а контейнер создаётся только при первом реально сохранённом компоненте. У конвейера единственный «сохраняемый» компонент -
   `MyHierarchyComponent` без детей, который возвращает `null`; ваниль всё равно создавала пустой контейнер,
   который не попадает в XML.

Проверенные и отвергнутые варианты:

- `GC.TryStartNoGCRegion` вокруг сборки снимка: перед входом делает полную блокирующую сборку, первое сохранение дало кадр 1008 мс;
- растянуть снимок на несколько кадров: сейв перестаёт быть атомарным, предметы, перенесённые между гридами, могут задвоиться;
- не создавать пустые списки пакетов в object builder конвейерных линий: загрузка и копирование гридов рассчитывают на непустые списки;
- не создавать второй пустой список секций конвейерной линии: реализовано и проверено (0 расхождений на 117 760 линиях), но экономия 0 -
  у линий этого грида поле секций `null`, а ~211 КБ на грид - это конструктор `MyObjectBuilder_ConveyorLine`. Патч убран.

Ловушка стенда: хуки Torch (prefix/suffix) на `MySession.Save`, `MySessionSnapshot.SaveParallel` и соседние методы
роняли процесс сервера без записи в лог в момент сохранения. Разбивку снимка по участкам снимали dotTrace, а не хуками.

## Результаты

| | кадр со снимком | сборки в этом кадре | выделения на грид | сохранение целиком |
|---|---:|---|---:|---:|
| ваниль | 135-151 мс | 6-7 gen0 + 2 gen1 | 604 КБ | 1.3-1.5 с |
| + параллельный снимок | 76-96 мс | 6-7 gen0 + 2 gen1 | 604 КБ | 1.2-1.4 с |
| + сериализация компонентов | 48-70 мс | 4-5 gen0 + 1 gen1 | 444 КБ | 1.2-1.4 с |
| + контейнер только при данных | **49-70 мс** | 4 gen0 + 1 gen1 | **416 КБ** | 1.2-1.4 с |

Выделения по типам блоков, байт на блок (ваниль → сейчас): конвейер 544 → 208 (остался только сам объект билдера),
завод 1504 → 976, реактор 1320 → 792, контейнер 925 → 573. Системы грида (конвейерные линии) - 211 КБ на грид, без изменений.

Что осталось в 976 байтах завода: объект билдера 272, агрегат из двух инвентарей 448, таймер 56, контейнер и записи ~200 -
всё это данные сейва.

Проверки на каждом прогоне: 0 расхождений у 32 064 блоков с эталоном и 0 расхождений параллельного снимка (51 МБ XML).
Выделения сократились на 31%, но число сборок в кадре снимка почти не изменилось: оставшихся ~27 МБ хватает на 4-5 бюджетов gen0.

## Открытые вопросы

- Оставшиеся 49-70 мс - в основном сборки мусора от ~27 МБ object builder. `COMPlus_GCgen0size=64 МБ` проверен: в кадре те же
  5 gen0, настройка не применилась; почему - не выяснено. Server GC и `NoGCRegion` не подходят (см. выше).
- На мире с сотнями тысяч блоков выигрыш параллельного снимка должен быть больше (больше гридов на все ядра); не проверено.
