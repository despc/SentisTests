# SentisTests

Плагин Torch для Space Engineers — стенд для проверки игры и наших плагинов (SentisOptimisations,
SentisGameplayImprovements, SentisAi, SentisWatcher, SentisAdventures, VirtualGarage) на живом сервере.
Сценарий спавнит в мир то, что нужно проверить, подключает при необходимости фейковых клиентов, гоняет
игру, замеряет кадры, выделения памяти, репликацию и проверяет результат. Всё созданное тестом удаляется
после прогона.

Плагин работает и на голом Torch, без остальных плагинов: там идут сценарии самой игры и Torch — сборка,
физика, производство, сварка, репликация, взрывы, безопасные зоны, программируемые блоки. Сценарии,
которые проверяют чужой плагин, при его отсутствии помечаются `SKIPPED` с причиной: не падают, мир не
портят, в `!test run all` не запускаются. Какие плагины что включают — в разделе «Чего плагин ждёт от
сервера».

Подробные отчёты по замерам производительности лежат в `docs/*.md` (на английском).

## Установка и настройки

Пример файла со всеми параметрами и комментарием к каждому: [`SentisTests.cfg.example`](SentisTests.cfg.example).

- Плагин кладётся в `Plugins\SentisTests`.
- `EventTimerLogs` (по умолчанию `false`, галочка на странице плагина): деревья вызовов медленных событий игры в логе.
  Выключено при старте — патчи EventTimer не ставятся вовсе; включение на ходу ставит их сразу.
- Настройки хранятся в `Instance\SentisTests.cfg`.
- Ставить только на тестовый сервер: сценарии меняют мир.

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `AutoRun` | `false` | Запустить сценарии сами после загрузки мира. |
| `AutoScenarios` | пусто | Какие сценарии запускать при `AutoRun` (пусто — все). |
| `AutoRunDelaySeconds` | `20` | Пауза после загрузки мира перед автозапуском. |
| `DefaultTimeoutSeconds` | `300` | Таймаут сценария, если сценарий не задал свой. |
| `CleanupAfterTests` | `true` | Удалять тестовые сущности после прогона. |
| `CleanupDelaySeconds` | `60` | Сколько тестовые сущности остаются в мире после сценария, чтобы их осмотреть; `0` — удалить сразу. При автоматическом прогоне удаляются сразу. |
| `ReportDirectory` | `SentisTests` | Куда писать отчёты (в `Instance`). |
| `EnableDebugBridge` | `false` | Включить локальный HTTP/MCP-мост. |
| `DebugBridgeToken` | пусто | Токен моста. Хранится только в конфиге стенда, никуда не публикуется. |
| `OwnerPlayerName` | пусто | Игрок-оператор, у которого сценарии ищут персонажа. |
| `IimBlueprintPath` | пусто | Чертёж дома с Isy's Inventory Manager для `pb_iim`; пусто или нет файла — `SKIPPED`. |
| `ProDumpPath` | пусто | `procdump64.exe` для снимка памяти при `CRASH DUMP`; пусто — ищется в `tools` рядом с сервером и в PATH. |

Владелец тестовых кораблей — игрок на сервере (`OwnerPlayerName` или любой подключённый), а без игрока — личность
`SentisTests`. Фейковые клиенты — свои личности. В мире с исследованиями и лимитами на игрока (мир прода: `EnableResearch`,
`PER_PLAYER`, 80 000 PCU на игрока) этим личностям открываются все исследования (`DebugUnlockAllResearchSync`) и даётся
запас в 20 млн PCU (`MyBlockLimits.AddPCU`): сварщик строит блок проекции, только если владелец его изучил и у него
хватает PCU. Без этого 14.10.2026 `mixed_weld` вставал на 53 блоках из 77, а `welder_spread` — на ~160 блоках из 2757.

## Сборка

Нужны игровые dll и Torch: папка установленного dedicated-сервера, рядом с ней `Torch.dll` (по умолчанию
`C:\SE`). Своя папка — `-p:SeRoot=D:\SE` или переменная окружения `SE_ROOT`; если Torch там нет, сборка так
и говорит, а не падает на сотне нерешённых имён.

```
cd SentisTests
dotnet build -c Release     # C# latest, net48; нужен .NET SDK 8+
```

Harmony (`lib\0Harmony.dll`, 2.1.1) лежит в репозитории и копируется в сборку: сам Torch Harmony не несёт,
поэтому плагин кладёт его рядом со своей dll.

Кроме `SentisTests.dll` и `0Harmony.dll` в `bin\Release` собираются `manifest.xml`, `LICENSE`, `NOTICE`,
готовая папка плагина `bin\Release\plugin\SentisTests` (с README) и архив
`bin\Release\SentisTests-<версия>.zip` — это и есть то, что отдаётся пользователю.

## Команды

| Команда | Что делает |
|---|---|
| `!test list` | Сценарии, доступные на этом сервере. |
| `!test list all` | Все зарегистрированные сценарии; недоступные помечены `— <причина>`. |
| `!test run <имя> [имя…]` / `!test run all` | Запустить один, несколько или все сценарии по очереди. |
| `!test run regression` | Все регрессионные проверки разом, каждая на своей площадке (см. «Регрессионные проверки»). |
| `!test stop` | Прервать текущий сценарий и очистить очередь. |
| `!test cleanup` | Удалить все тестовые сущности, оставшиеся в мире. |
| `!test status` | Текущий сценарий и последние результаты. |
| `!test results` | Все результаты этой сессии. |
| `!add_bot` | Фейковый игрок в 10 м перед тобой: пока он там, физика твоего кластера шагает и фризер его не морозит. Любой запуск `!test run` их убирает. |
| `!remove_bots` | Убрать всех фейковых игроков — и своих, и оставленных тестами (сценарий, идущий сейчас, своих тоже лишится). |

Результат каждого сценария — строка `[TEST] PASSED|FAILED|SKIPPED <имя> (время) — итог` в логе Torch.
Отчёты пишутся в `ReportDirectory`.

## Чего плагин ждёт от сервера

Обязательно только то, на чём уже стоит Torch: игровой dedicated-сервер и Torch. Больше ничего.

Опционально — наши плагины; каждый включает свою группу сценариев. Без плагина его группа помечается
`SKIPPED` с причиной (`SentisOptimisations is not loaded`) и в `run all` не попадает вовсе. Точный список
на конкретном сервере — `!test list all`.

| Плагин | Что он включает |
|---|---|
| `SentisOptimisations` (SO) | фризер гридов и физики, бюджет кадров производства, выборочная физика, наказание ПБ, параллельное сохранение, правка патчей Torch: `freeze_*`, `freezer_*`, `production_freezer_stress`, `refinery_perf_busy`, `physics_resume`, `unstepped_blocks`, `power_switch`, `panel_server`, `pb_*`, `frozen_radius_weld`, `piston_stack`, `laser_*`, `remote_control_anchors` |
| `SentisGameplayImprovements` (SGI) | взрывы, лимит PCU, возврат провалившихся гридов, цены контрактов, PvE-зона, поле астероидов, застревание в вокселях, цена резака: `explosions`, `pcu_limit`, `pcu_limit_cost`, `pve_zone`, `wheel_*`, `fall_through_tunnel`, `wreck_restore`, `contract_prices`, `voxel_stuck`, `asteroid_field`, `world_sweeps` |
| `SentisAi` | боты: `bot_*` и `ai_status_ui` |
| `SentisWatcher` | записи и учёт: `watcher_record`, `watcher_load`, `watcher_ledger` |
| `SentisAdventures` | NPC и генераторы приключений: `npc_spawn`, проход поведенческих блоков в `world_sweeps` |
| `VirtualGarage` | `garage_roundtrip` |
| `SentisTranslator` | перевод чата моделью стенда: `translator_chat`, `translator_restart`; посмотреть самому: `translator_say`, `translator_say_inline`, `translator_say_discord` |
| `Profiler` | профилирование внутри `load_test` и `freezer_stress_profile`; без него эти сценарии идут и пишут `PROFILE: the Profiler plugin is not loaded here` |

Ещё три внешних условия:

- чертёж корабля Spitfire встроен в плагин (`SentisTests/Resources/Spitfire.xml`) — гриды в мире для
  сварочных и сетевых сценариев не нужны;
- `pb_iim` просит чертёж чужого дома с Isy's Inventory Manager — `IimBlueprintPath` в конфиге; без пути или
  без файла сценарий `SKIPPED`;
- `procdump64.exe` нужен только для снимка памяти при `CRASH DUMP` (`ProDumpPath`, иначе ищется в `tools`
  рядом с сервером и в PATH); без него в логе одной строкой больше, остальное пишется и так.

## DebugBridge

Локальный мост для осмотра мира и управления гридами из скриптов и агентов. Слушает только `127.0.0.1`,
каждый запрос требует токен (`DebugBridgeToken`, не короче 32 символов, иначе мост не запускается). Всё, что трогает мир, выполняется на игровом потоке.

REST:
- `GET /grids`, `/grid?id=`, `/at?x=&y=&z=&r=` — гриды и что вокруг точки;
- `POST /move`, `/orient`, `/vel`, `/delete`, `/park`, `/unpark` — двигать, поворачивать, задавать
  скорость, удалять, держать грид в точке;
- `POST /test {name}` — поставить сценарий в очередь;
- `GET /status`, `GET /log?n=` — состояние и хвост лога;
- MCP (JSON-RPC поверх SSE) на `/mcp/sse` и `/mcp/message` — те же возможности как инструменты.

## Инфраструктура

- **`TestScenario` / `TestRunner`.** Сценарий — корутина по кадрам: шаги, ожидания условий с таймаутом,
  проверки (`Check`), заметки в лог (`Note`). Раннер ставит сценарии в очередь, ловит исключения,
  вызывает `Cleanup()` и удаляет всё, что сценарий пометил (`Track`), и всё с префиксом `ST-47351-`.
- **`WorldApi`.** Спавн гридов из object builder, чертежей, встроенных ресурсов и авторских гридов мира
  оператора; поиск блоков; снятие паузы мира.
- **`FakeClients`.** Внутрипроцессные фейковые клиенты с игроком и персонажем, эмуляцией сети (RTT,
  потери) и движением. Сервер реплицирует им мир как настоящим, а тест видит, что каждому клиенту
  отправлено: `ArrivedCount`, `Arrivals`.
- **`TickMetrics`, `FrameProbe`, `AllocProbe`.** Время кадра симуляции (среднее, p95/p99/p99.9, максимум,
  число кадров > 16.7/33.3 мс), время отдельных методов, выделения памяти.
- **`SafeZoneProbe`.** Хуки безопасных зон на время сценария: проверки форм, события фантома, обновление
  зоны, блокировки моторов, стоимость отслеживания гридов SentisOptimisations, что зона разослала клиентам.
- **`LeaveTargets`.** Разбор IL на ошибку перевыпуска `leave` в Torch (для `patch_audit`).
- **`tools/`.** Скрипты извлечения гридов из сейва в ресурсы и проверки контрактов метрик.

## Регрессионные проверки

`regression` — набор проверок (318, и ещё те, что добавляют другие плагины стенда) базовых механик игры, каждая в том виде, в каком с ней сталкивается игрок: поставить
блок, сварить, разобрать, перенести предметы, полететь, запустить реактор и завод и так далее. Проверки идут разом,
каждая на своей площадке, весь набор занимает около 2 минут. Площадки стоят через 8 км (в космосе квадрат 19 на 19 вне
гравитации, на Марсе квадрат 6 на 6 в 8 км от anchor-а `wheel_perf`): дальше размера кластера физики SentisClusters
(5 км), поэтому каждая проверка лежит в своём кластере, и потоки кластеров обновляют их параллельно. Над площадками в
космосе пусто: проверки уводят туда свои гриды (полосы оружия на 5-36 км, прыжки). Дольше всех идёт безопасная зона: по правилам игры у
неё 120 с отсчёта. Остальные укладываются в 20 с.

Запуск:
- `python C:/SE/tools/run_regression.py` — весь набор; `python C:/SE/tools/run_regression.py reactor,hand_` —
  только проверки, в имени которых есть одно из слов. В конце печатаются строки всех проверок, сначала
  непрошедшие, и итог. Код выхода 0 — всё прошло (или пропущено);
- `!test run regression`, через DebugBridge — `POST /test {"name":"regression","focus":"reactor,hand_"}`;
- одна проверка отдельно — `!test run reg_reactor` или `run_scenario.py reg_reactor` (строится на площадке 0).

Каждая проверка пишет в лог свою строку `[TEST] PASSED|FAILED|SKIPPED reg_<имя> (время) — итог`, сьют — строку
`REGRESSION RESULT | N passed, M not …` с причинами и `[TEST] PASSED|FAILED regression`. В `run all` проверки
по одной не входят: их прогоняет `regression`.

Как устроено (`SentisTests/Regression`):
- **Площадки** (`Site.cs`):
  - в космосе — квадрат по 8 в ряд через 1 км, за пределом гравитации планеты стенда;
  - на планете — ряд через 300 м по поверхности, в 3 км от якоря `wheel_perf`.
- **Свой фейковый игрок.** Он стоит рядом (фризер не трогает площадку), владеет построенным и действует. Его
  действия идут путями игры:
  - запрос клиента вызывается на сервере в контексте этого клиента (`Request`: обработчик события, как его вызывает
    сеть, без её проверки доступа);
  - клавиши персонажа и корабля — пакетом управления клиента (`Keys`, `ShipKeys`, как `DeserializeControls`);
  - ручной инструмент — `SwitchToWeaponMessage`, `ShootBeginCallback`, `ShootDirectionChangeCallback`.

  Что патчат плагины на этом пути, проверяется вместе с игрой.
- **Гриды** строятся из частей (`Part`: блок, клетка, куда смотрит) и спавнятся как вставка. Питание, конвейеры и
  остальное игра подключает сама. Где порты конвейера берутся из модели, место соседа подбирается перебором
  (`ConveyorNeighbour`). Инструмент ставится так, чтобы цель попала в сферу его сенсора (`ToolRig`).
- **Время.** Удержания клавиш, паузы и ожидания (`Until`) считаются в кадрах игры (60 в секунду), а не по часам: на
  нагруженном сервере игра идёт медленнее. `Until` ждёт не дольше чем вчетверо больше по часам.
- **Урон.** SentisGameplayImprovements после старта на время блокирует весь урон. Сьют на время прогона ставит
  `DisableAnyDamageAfterStartTime = 0` и потом возвращает. Отдельная проверка с уроном (`NeedsDamage`) делает так же.
- **Рассыпанные предметы.** Сверх `MaxFloatingObjects` (на стенде 50) уборка SGI закрывает рассыпанные предметы
  наугад, свежие тоже, а выпадения проверок разом этот лимит переходят: у `collector` и `floating_lifetime` пропадали
  их же пластины. Сьют на время прогона поднимает лимит до недостижимого, отдельная проверка с выпадением
  (`NeedsLooseItems`) делает так же.
- **Мешки погибших.** Essentials ограничивает мешки на игрока (`BackpackLimit`, на стенде 1), но владельца мешка
  читает, когда мешок появляется в мире, а игра ставит владельца уже после этого. Все мешки для Essentials — ничьи,
  и сверх лимита он через 30 с закрывает все, кроме самого нового на сервере: у `death_loot` пропадал мешок с
  пластинами, когда в сьюте умирал кто-то ещё. Сьют на время прогона делает лимит недостижимым (`int.MaxValue`), отдельная
  проверка с мешком (`NeedsBags`) делает так же. Не -1: при -1 Essentials не отслеживает только новые мешки, а уже
  отслеженные (стенд стартует с 1) удаляет до пустого списка и падает на каждом кадре (`ProcessBags`).
- **Мусор прошлых прогонов.** Прогон, который не закончился (сервер упал), оставляет на площадках рассыпанные предметы,
  а перезапуск стенда сохраняет мир вместе с ними. Колесо 5x5 из `all_blocks_large` не вставало туда, где они лежали,
  а в кластере, отцеплённом вручную, вставало прямо в них. Перед проверками сьют убирает рассыпанные предметы в 300 м
  от каждой площадки.
- **Отцеплённые кластеры (SentisClusters).** Проверки меняют игру прямо с игрового потока. Сеть делает то же самое, и
  её запросы SentisClusters заставляет ждать тик сущности. Поэтому перед каждым шагом проверок сьют ждёт идущие тики
  (`ClustersApi.WaitForDetachedTicks`). Фокус `detach=1` вручную отцепляет кластер каждой площадки.
- **Исключения в проходе обновлений.** Во время прогона `DispatchWatch` считает исключения, вылетевшие из прохода
  игры по обновлениям сущностей (`MyParallelEntityUpdateOrchestrator.DispatchBefore/AfterSimulation`): такое исключение
  обрывает проход, и все сущности после той, что бросила, в этом кадре не обновляются. SO глушит их (`CrashFixPatch`) и
  пишет в лог только с диагностическими логами; здесь они видны всегда, каждое вид пишется в лог, и регрессия падает.
- **Новая проверка** — класс-наследник `RegressionCheck` в `Regression/Checks`: `Kind` (`Space`/`Planet`), `Check()`.
  Плюс строка в `Regression/Registry.cs`. Проверку из другого плагина добавляет `Registry.AddCheck` (в его `Init`).

Проверки:
- **Строительство:**
  - `reg_place_block` — блок с меню строительства на грид, каркасом, первый компонент взят у игрока;
  - `reg_place_grid` — блок в пустоте, новый грид игрока;
  - `reg_radiation_deleted_character` — отложенный урон от радиации у персонажа, удалённого в тот же кадр: сервер не
    падает. Сначала проверяет, что защита SO (`CrashFixPatch`) стоит на отложенном вызове: без неё сервер упал бы, и
    шаг не делается;
  - `reg_rejoin` — игрок выходит и заходит снова (один клиент, остальные остаются): персонаж стоит где был, с 7
    пластинами, сидевший — в кокпите; после входа у каждого свой персонаж, сидевший управляет кокпитом. Выход и вход по
    одному клиенту — `FakeClients.Quit`/`Rejoin` (вход — `OnNewPlayerRequest` и запрос возрождения с `JoinGame`, как у игры);
  - `reg_block_transfer` — передача блоков другому игроку: ждёт его согласия, согласие третьего ничего не меняет, после
    согласия блоки его; запрос с несуществующим блоком не бросает исключение (SO `OwnershipRequestCheck`);
  - `reg_remote_block_removal` — удаление своих блоков издалека («X» у грида во вкладке «Инфо», при
    `EnableRemoteBlockRemoval`): с 400 м уходят 3 блока игрока, 3 блока другого строителя остаются. Пока в 10 км от грида
    есть игрок-враг, SGI удаление запрещает (`RemovePluginPatch`), и в сьюте проверка ждёт этот отказ;
  - `reg_timer_group` — таймер с действием группы блоков: выключаются три лампы группы, лампа вне группы горит;
  - `reg_relative_dampeners` — гасители относительно корабля, дрейфующего 10 м/с: персонаж держит его скорость, после
    сброса останавливается;
  - `reg_drill_ores` — корабельный бур в кубе вокселей каждого материала (по одному на каждую руду, 11): каждый бур
    накапывает только руду своего материала (`MinedOre`);
  - `reg_defensive_combat` — оборонительный блок ИИ на дроне (бегство по своим координатам, «всегда» — когда нашёл
    врага): находит вражескую станцию в 150 м и уводит дрон к координатам;
  - `reg_cleanup_exception` — исключение уборки мусора SGI (`IgnoreCleanupSubtypes`, в памяти «Container»): грид с
    ящиком не попадает в гриды ванильной уборки (`MySessionComponentTrash`), грид из брони — попадает. На стенде в
    настройке «Cargo», а такого нет ни в одном ванильном подтипе;
  - `reg_auto_rename`, `reg_online_reward`, `reg_floating_lifetime` — функции SGI: грид с именем «Large Grid 1234»
    получает имя владельца (`AutoRenameGrids`), свой — остаётся; награда за онлайн приходит один раз за интервал
    (`OnlineReward*`, интервал 1 мин в памяти); своя уборка плавающих объектов убирает стопку старше
    `FloatingObjectsLifetime` (время её появления, как SGI его записала, сдвинуто на 10 мин назад), свежую оставляет;
  - `reg_claim_npc_ownership` — «Заявить права» на NPC-грид: в игре игроку переходят PCU, а батарея остаётся за NPC; с
    SGI `ClaimNpcGridTakesOwnership` (включается в памяти) батарея — игрока, ничей ящик остаётся ничьим;
  - `reg_hand_weld`, `reg_hand_grind` — ручные сварщик и резак: каркас до конца, блок в ноль, все 25 пластин
    у игрока;
  - `reg_hand_grind_full` — резак со скафандром, полным камня: блок срезается всё равно, все 25 пластин выпадают у него
    предметами (`SpawnConstructionStockpile`), в скафандре ни одной;
  - `reg_weld_without_components` — без компонентов сварка доходит только до того, что дают компоненты самого каркаса, и
    встаёт;
  - `reg_ship_weld`, `reg_ship_grind` — то же корабельными, включёнными в терминале;
  - `reg_projector` — голограмма сдвинута, как игрок её двигает, и сварена в грид проектора;
  - `reg_projector_subgrid` — чертёж с подгридом (блок и ротор с головой): сварка ставит ротор, голова садится на него
    своим гридом (блоки на гриде головы игра из проекции не строит);
  - `reg_paint` — покраска одного блока;
  - `reg_hand_drill` — ручной бур в астероид из ассетов игры: руда сыплется кусками у отверстия (вырез бура в 1 м
    от головы, ровную землю под ногами он не берёт);
  - `reg_ship_drill`, `reg_ship_drill_small` — корабельный бур, руда в его инвентаре с планеты; вырытое возвращается;
  - `reg_ship_weld_small`, `reg_ship_grind_small` — малые корабельные сварщик и резак;
  - `reg_welder_conveyor` — корабельный сварщик берёт пластины из ящика на своём конвейере и доваривает каркас;
  - `reg_hand_tool_tiers` — ручные сварщики и резаки всех четырёх уровней: работают, следующий не медленнее.
  - `reg_block_limits` — лимит мира по тегу (буры на игрока): бур номер N (лимит) пристраивается к гриду, следующий — нет.;
  - `reg_pcu_accounting` — PCU контейнера засчитывается игроку, когда блок доварен (у каркаса 0), и снимается после разборки.
- **Терминал и инвентари:**
  - `reg_terminal` — переименование блока и грида, свет выключить и включить, радиус, «поделиться со всеми» и
    обратно, группа блоков;
  - `reg_gps` — GPS-метки игрока, как их шлёт клиент: добавленная попадает в список отправителя (а не той личности,
    что названа в запросе), переименованная и перенесённая остаётся одной записью, пишется в сохранение, удаление
    чужим игроком её не трогает, своё — убирает;
  - `reg_inventory_transfer` — перенос между ящиком и игроком, количества точные;
  - `reg_access_rights` — что сервер пускает игрока делать, по своей сетевой проверке запроса (`Rights`: флаги
    `[Server(ValidationType…)]` события → `HasRights` реплики цели, как `MyReplicationServer`): взять из своего ящика рядом
    и переименовать его — да; из чужого (ни с кем не поделён) — нет (`Ownership`); из своего в 300 м — нет (`Access`); из
    своего в 300 м с антенной на его гриде — да (терминал через антенну). Из скафандра в чужой ящик ничего не кладётся,
    в свой — кладётся;
  - `reg_cargo_capacity` — объём ящика: из определения (или по размеру блока) × множитель инвентаря мира, лишнее не берёт;
  - `reg_ownership` — блок отдан другому игроку, тот принял предложение;
  - `reg_programmable_block` — скрипт с аргументом выключает свет (пропуск, если скрипты в мире выключены);
  - `reg_programmable_self_run` — скрипт с `UpdateFrequency.Update10` запускается сам, без «Run»;
  - `reg_programmable_limits` — скрипт с бесконечным циклом обрывается на лимите инструкций (50 000, «too
    complex»), скрипт с исключением останавливается, сервер идёт дальше; после перекомпиляции скрипт снова работает;
  - `reg_button_panel`, `reg_timer`, `reg_sensor` — кнопка и таймер выключают свет, сенсор видит игрока и
    отпускает;
  - `reg_sensor_relations` — фильтры сенсора по отношениям: «владелец» видит игрока и не видит чужого, «враги» —
    наоборот, без обоих — никого;
  - `reg_conveyor` — завод на конвейерах: руду, уран и железо блоки тянут сами;
  - `reg_use_conveyor_off` — реактор с выключенной «Use conveyor system» не берёт уран из ящика, включённый — берёт;
  - `reg_turret_ammo_conveyor` — турель сама берёт магазины из ящика на своих конвейерах;
  - `reg_grind_container` — корабельный резак, разобрав ящик, забирает и его содержимое;
  - `reg_conveyor_push` — очиститель и сборщик отправляют выпуск в ящик на конвейере, когда их выходной инвентарь заполнен
    больше чем на 75 % (раньше игра его не выталкивает);
  - `reg_lcd_text` — текст LCD (и тип содержимого, и размер шрифта) переживает сохранение;
  - `reg_small_conveyor` — малая конвейерная линия пропускает компоненты, но не предметы больше 0,25 м (балка, 1 м);
    большая пропускает всё;
  - `reg_sorter` — сортировщик сливает руду и оставляет пластины;
  - `reg_connector` — стыковка и расстыковка, ящик корабля на конвейере станции только при стыковке;
  - `reg_connector_trading` — коннектор в режиме торговли: конвейер через него не идёт (`IsConnectedTo`,
    `TransferItemTo`), без режима идёт; после расстыковки пара какое-то время не сцепляется;
  - `reg_merge` — два грида, касающиеся только мёрж-блоками, сливаются в один; выключенный мёрж-блок снова разделяет их, и
    отделившийся кусок (статичный, как станция, к которой он прирос) переводится в корабль и двигается;
  - `reg_drop_pickup` — 8 пластин выброшены и подобраны;
  - `reg_collector` — коллектор забирает парящее перед ним;
  - `reg_grid_split` — без среднего блока линия распадается на два грида;
  - `reg_faction` — фракция создана, второй игрок принят: ящик фракции открыт ему и закрыт чужому, вышедшему — закрыт;
  - `reg_faction_relations` — две фракции игроков: сначала война, запрос мира висит, пока другая сторона не примет, потом
    нейтралитет, объявление войны — снова война. Дружбу игрокам не предложить: в терминале нет кнопки, а сервер принимает
    `AcceptFriendRequest`, только когда фракции уже друзья;
  - `reg_faction_ranks` — простой участник не может выгнать другого; основатель повышает его до лидера, понижает и снова
    повышает; лидер выгоняет участника;
  - `reg_faction_bank` — счёт фракции: участник кладёт 3000, лидер снимает 1000, снять простому участнику сервер не даёт
    (`IsFactionValid`);
  - `reg_grid_storage` — хранилище гридов терминала услуг: корабль игрока с 10 пластинами в ящике убран (уходит из
    мира, появляется запись игрока) и возвращён сразу: снова в мире у терминала, игрока, с пластинами, запись удалена;
  - `reg_save_roundtrip` — грид записан, как его пишет сохранение (билдер → XML → обратно), и сделан заново: предметы,
    очередь сборщика, заряд, газ, имена, переключатели, custom data, тулбар таймера на свой свет, группа, скрипт ПБ;
  - `reg_connector_throw_out` — коннектор с «Собрать всё» стягивает камень из ящика и с «Выбросить» выкидывает его;
  - `reg_small_connector_throw_out` — малый коннектор (бывший эжектор) выкидывает свой груз;
  - `reg_convert_grid` — станция в корабль (двигается от толчка) и обратно (стоит).
- **Энергия и производство:**
  - `reg_reactor` — реактор жжёт уран и питает завод, выключенный — завод встаёт;
  - `reg_battery` — заряд от реактора и разряд на завод;
  - `reg_power_priority` — нехватка энергии по приоритетам групп: 21 искусственная масса (Utility, 12,6 МВт) на

    массы выключены — 19 помещаются, двигателю меньше;
  - `reg_grid_power_switch` — кнопка питания грида выключает свои источники и общие для всех, чужую батарею без
    доступа не трогает; включает обратно;
  - `reg_solar`, `reg_wind` — панель на солнце, ветряк в атмосфере;
  - `reg_hydrogen` — лёд в O2/H2-генераторе, бак наполняется, водородный двигатель даёт ток;
  - `reg_bottle` — генератор с «Автозаправкой» наполняет баллон;
  - `reg_refinery` — выход слитков точно по чертежу и эффективности;
  - `reg_assembler` — 10 пластин по чертежу с учётом множителя мира, разборка 5 обратно;
  - `reg_survival_kit` — пластины в наборе выживания;
  - `reg_basic_refinery` — простой очиститель (Blast Furnace) по своему чертежу и эффективности;
  - `reg_production_tiers` — уровни производства: базовый сборщик не берёт в очередь чертёж большого (запрос клиента
    `OnAddQueueItemRequest`) и берёт свой; Blast Furnace переплавляет железо и не трогает платину;
  - `reg_upgrade_modules` — модули продуктивности, эффективности и энергии на очистителе (место модуля — по точкам
    подключения из моделей): каждый меняет только своё, с модулем эффективности слитков больше по формуле;
  - `reg_refinery_all_ores` — все руды очистителя (11): каждый результат каждого чертежа по выходу и эффективности;
  - `reg_assembler_all_components` — все компоненты сборщика (22): один прогон чертежа даёт его выход (пластины — по
    140 за раз, конструкционные — по 3), расход по чертежу с множителем мира;
  - `reg_assembler_repeat` — режим повтора: одна пластина в очереди делается снова и снова;
  - `reg_assembler_cooperative` — второй сборщик в кооперативном режиме забирает часть очереди первого;
  - `reg_survival_kit_stone` — камень в наборе выживания: гравий и немного железа, никеля, кремния;
  - `reg_generator_pulls_ice` — генератор сам тянет лёд из ящика по конвейеру, водород идёт в бак;
  - `reg_gas_tanks_fill` — 33 пары «генератор + бак», лёд в каждую на 3 кадра позже: каждый бак держит отданный ему
    газ (ловит баг SO `GasTankOptimisations`, после которого бак переставал наполняться навсегда);
  - `reg_tank_refill` — полный бак заправляет пустой баллон по кнопке «Refill»;
  - `reg_oxygen_farm` — кислородная ферма, повёрнутая к солнцу, вырабатывает больше половины своего; боком — почти ничего.
  - `reg_battery_modes` — батарея на «Recharge» только берёт ток, на «Discharge» только отдаёт (питает свет без реактора);
  - `reg_algae_farm` — водорослевая ферма на солнце делает водоросли (время партии ускорено);
  - `reg_solar_shadow` — солнечная панель в тени стены даёт почти ничего;
  - `reg_food_processor` — кухонный комбайн готовит паёк чили из 3 овощей и фрукта по чертежу;
  - `reg_farm_plot` — ирригация из льда наполняет грядку водой (через конвейерный порт грядки, он у неё компонентом);
    семена посажены игроком, растут на воде, урожай (время роста ускорено) собран в скафандр.
- **Движение и механизмы:**
  - `reg_jetpack` — полёт на джетпаке, расход водорода, остановка гасителями;

  - `reg_ladder` — по лестнице из шести секций вверх больше 3 м;
  - `reg_parachute` — малый корабль падает в атмосфере, открытый парашют гасит скорость до нескольких м/с (канва расходуется);

  - `reg_planet_breath` — на планете с пригодным воздухом (EarthLike; площадки стенда на Марсе, где воздуха нет) с открытым

  - `reg_eat` — паёк из инвентаря съеден: пайка нет, сытость растёт; второй, пока первый действует, игра не даёт;
  - `reg_hunger` — при нулевой сытости игрок теряет здоровье от голода;
  - `reg_radiation` — целый реактор не излучает, повреждённый — поднимает радиацию игрока рядом;
  - `reg_spherical_gravity` — сферический генератор гравитации тянет игрока к центру;
  - `reg_artificial_mass` — корабль с искусственной массой падает в поле генератора гравитации, с выключенной — стоит;
  - `reg_thrust_environment_planet`, `reg_thrust_environment_space` — атмосферный двигатель на планете даёт ~90 % тяги,
    ионный ~25 %; в космосе атмосферный 0, ионный 100 %;
  - `reg_breathing_room` — с открытым шлемом в комнате с воздухом персонаж не ранится, кислород костюма не тратится;
  - `reg_cockpit_oxygen` — в кабине с кислородом костюм наполняется из её запаса;
  - `reg_jetpack_gravity` — джетпак в гравитации планеты держит персонажа и поднимает его;
  - `reg_ship_flight` — тяга по клавишам пилота, гасители, поворот гироскопом, расход батареи;
  - `reg_hydrogen_thrust` — водородные двигатели от бака;
  - `reg_tank_stockpile` — бак в режиме накопления не отдаёт водород двигателям, корабль стоит; без накопления летит;
  - `reg_thruster_flame` — пламя двух двигателей спиной к спине (тяги гасят друг друга) повреждает стены перед соплами;
  - `reg_hover` — атмосферные двигатели держат корабль и поднимают его;
  - `reg_wheels` — ровер `wheel_perf` едет по полу (колёса ограничены 20 км/ч, чтобы не уехать с площадки), колёса
    поворачивают, тормоза останавливают, на ручнике не едет;
  - `reg_rotor`, `reg_piston`, `reg_hinge` — голова добавлена «Add Head», движение в обе стороны; у ротора ещё голова
    отсоединена и присоединена снова;
  - `reg_rotor_lock`, `reg_hinge_lock` — заблокированные ротор и шарнир держатся при заданной скорости, разблокированные

  - `reg_speed_limit_large`, `reg_speed_limit_small` — корабль, разогнанный до 300 м/с, держится на пределе мира (100 м/с
    выходят 104,4 у Havok);
  - `reg_overrides` — корабль без пилота: перехват гироскопа поворачивает, перехват тяги толкает;
  - `reg_landing_gear` — шасси держит корабль на полу и отпускает;
  - `reg_landing_gear_ship` — шасси малого корабля цепляется за дрейфующий большой и едет с ним, отпущенное отстаёт;
  - `reg_gravity_generator` — 9,81 м/с² в поле, ноль снаружи, персонаж падает;
  - `reg_jump_drive` — прыжок на 20 км после отсчёта;
  - `reg_jump_drive_charge` — пустой прыжковый двигатель заряжается от батарей;
  - `reg_remote_autopilot` — удалённое управление с точкой в 150 м летит туда на автопилоте и останавливается.
- **Автоматика и связь:**
  - `reg_camera_raycast` — камера сканом находит блок в 50 м впереди;
  - `reg_antenna_message` — сообщение IGC скрипта доходит до станции в 300 м через антенны, при радиусе 100 м — нет;
  - `reg_antenna_unicast` — адресное сообщение IGC (`SendUnicastMessage`) с борта доходит по антеннам до адресата

    транспондер на 8 только слышит, чужой срабатывает лишь с фильтром «от всех»;

Что игра делает не так, как кажется, и что проверки учитывают:
- конвейеры грида без питания не соединяют ничего;
- облучение (радиация блоков, солнце, погода — всего 5 источников) игра считает за кадр одному игроку от одного источника.
  Больше чем при 100 / (источников) игроках онлайн (20) она берёт игрока и источник по одному счётчику кадров
  (`MyHazardExposureComponent.PlayersAndSourcesStaggered`: кадр % игроков, кадр % источников). **Ошибка игры:** если у
  числа игроков и числа источников есть общий делитель, пара «игрок — источник» встречается не для всех: при числе игроков,
  кратном 5, каждый игрок получает только один источник из пяти, остальные — никогда (так на стенде: 225 игроков, игроку
  №93 радиация от блоков не считается вовсе). `reg_radiation` в таком случае пропускается с объяснением, иначе ждёт до 90 с;
- на низком качестве симуляции (его игра ставит сама при загрузке выше 90 %, `AdaptiveSimulationQuality`) столкновения
  гридов не обрабатываются (`MyGridPhysics`: ни урона, ни смятия), и под нагрузкой большие гриды на 50-60 м/с проходили
  друг сквозь друга без урона; пули на низком качестве проверяют, во что попали, раз в 15 кадров вместо 5
  (`MyProjectile.CHECK_INTERSECTION_INTERVAL`) и пролетают стены (под нагрузкой пистолет расстреливал магазины мимо).
  Проверки столкновений, кратера и оружия держат качество высоким (`HoldHighQuality`, общий счётчик: адаптивность
  возвращается, когда отпустит последняя);
- грузовой корабль NPC без пульта и без AI-блоков ведёт простой автопилот игры (`MySimpleAutopilot`): тяги он не даёт,
  корабль летит на скорости, с которой появился. Фризер SO, заморозив такой корабль (дальше 10 км от игроков), обнуляет
  ему скорость (`FreezeLogic`, `SetSpeeds`), и после разморозки он стоит до конца своих 30 минут. `reg_cargo_ship` в этом
  случае падает с этой причиной;
- при смерти инвентарь тела очищается, а мешок с вещами встаёт в очередь спавна (`MyFloatingObjects`, по нескольку за
  кадр): под нагрузкой вещей какое-то время нет нигде;
- при разборке блока компонент с `DeconstructId` в определении (силовые элементы, детали Prototech) превращается в то,
  что там указано (металлолом);
- чертёж может давать за один прогон несколько штук: стальные пластины — 140, конструкционные — 3;
- новый тренировочный манекен стоит сбитым, пока ему не дать стальную пластину;
- паук вылезает из-под земли только рядом с первым онлайн-игроком на «паучьей» планете (не обязательно рядом с тем, на
  кого он вызван);
- закрытый грид ждёт удаления в сцене вместе с физикой: в него попадают пули, он затеняет панели, с ним сталкиваются.
  SO `EntityDeleteBudget` на нагруженном сервере удаляет одну сущность за кадр, и после уборки регрессии (около 2600
  гридов разом) закрытые стоят больше минуты: пистолеты `reg_hand_weapons` стреляли в закрытую стену вместо новой.
  Поэтому набор удаляет закрытое сразу, без бюджета: после уборки каждой проверки и там, где проверка закрывает грид и
  строит новый на том же месте (`CloseAndWait` — пистолеты, солнечная панель, шасси, столкновения), вызывается игровой
  `MyEntities.DeleteRememberedEntities` вне конца кадра (там SO не вмешивается, удаляется всё). Уборка — один длинный
  кадр, для стенда это не важно. Проверка самого удаления SO (`ClosedGridGoneCheck`, 600 гридов при нагруженных кадрах)
  в набор не включена: с нынешним SO она красная;
- набором не покрыты: управление кораблём через
  пульт (связь антенн для фейкового клиента не находится), глобальные встречи (игра ставит их в случайное место мира на
  90 минут — это менять мир для настоящих игроков);
- грузовой корабль NPC игра ставит на край коробки 8 км вокруг игрока (до ~14 км, коробка ещё растёт на игроков рядом);
  дальше 10 км от игроков фризер SO его держит (`FreezeDistanceDynamic`), полетит он, когда игрок подойдёт;
- отсчёт безопасной зоны идёт по игровому времени (`TotalGamePlayTimeInMilliseconds`);
- малый конвейер не пропускает предмет, у которого наибольший размер больше 0,25 м (`MyGridConveyorSystem.NeedsLargeTube`);
- ложная цель (decoy) относится к группе целей «Weapons»: турель с группой по умолчанию сначала бьёт батареи и прочее;
- контракт на ремонт игра закрывает и оплачивает сама, как только блоки заварены; контракт на перевозку выдаёт посылку
  при взятии;
- корабельные инструменты ставятся выключенными;
- флажок терминала «Safety» у боеголовки — это взведена она или нет;
- `MyPlanet.GetOrePriority()` = −1: ручной бур не режет планету (руду с планеты даёт только корабельный бур), режет
  астероиды; руду ручной бур сыплет кусками;
- тонкие гриды на скорости проходят сквозь то, во что бьются: контакт снимается ради смятия (`BreakImpulse` =
  масса × 2);
- генераторы гравитации стягивают свободные гриды рядом;
- турели стреляют по гридам любых других игроков: оружие проверяется вдали от остальных площадок;
- `NeedsOxygenFromSuit == true` означает открытый шлем;
- только что взятый в руки инструмент пару кадров без питания, и нажатие не проходит: проверка жмёт ещё раз, как
  игрок;
- ручной бур берёт направление из того, что прислал клиент;
- SGI не даёт кинетического урона от гридов легче `MinimumMassForKineticDamage`: проверки на время прогона ставят 1;
- пока конвейерные пути грида не посчитаны (это делается в фоне, после постройки или изменения),
  `MyGridConveyorSystem.PullItem` ничего не переносит и сообщает об успехе: покупка в только что поставленном магазине
  забирает деньги и ничего не даёт. `PushGenerateItem` в первый раз только запускает расчёт: первая сдача контракта на
  свежей базе — «нет места», вторая проходит;
- модуль улучшения ищет, к чему он подключён, раз в 100 кадров;
- связь антенн пересчитывается раз в ~100 кадров;
- криокамера и кресло — кабины: в них дышат их воздухом, если он есть;
- у фейковых игроков банковский счёт заводит `FakeClients`, как игра заводит его входящему игроку;
- колесо подвески ставится только на свободное место (`TestPlacementForWheelWhenPlacingWheel`), а удаление гридов под
  нагрузкой ждёт своей очереди: `reg_all_blocks_*` строит каждую партию блоков на своей высоте, иначе колёса новой партии
  упирались в ещё не удалённую прошлую;
- тормоз колёс пилот включает у себя (`TryEnableBrakes`), на сервер его приносит синхронизация каждого колеса;
- ModAPI `IMyFlightMovementBlock.AddWaypoint` на сервере бросает исключение («Event 'AddWaypointBroadcast' not found»):
  точки блоку отдаёт `MyFlightMovementBlock.SetWaypoints`, как рекордер и базовая задача;
- турельный контроллер стреляет, как только цель в пределах его допуска (`AngleDeviation`, 5° в чертеже): по маленькой
  цели вдали он мажет; цели-персонажи в чертеже включены, и фейковый враг рядом со своей станцией становится целью сам;
- первый быстрый удар грида в место планеты без построенной физики может пройти сквозь неё;
- магнитные ботинки включаются, только когда ноги стоят на гриде (`CharacterProxy.Supported`): персонаж, поставленный
  чуть над полом, в невесомости так и висит «Falling»; игрок опускается на пол джетпаком и выключает его;
- обычный ротор конвейер не пропускает (у `MyMotorRotor` нет конвейерного порта), продвинутый, шарнир и поршень пропускают;
- кокпит ведёт двигатели и гироскопы только своего грида; двигатели на подгриде слушают кресло на этом подгриде;
- блок, не держащийся монтажными точками (лампа сбоку батареи), игра снимает вместе с соседом при любой разборке;
  блоки при расколе грида переходят в новый грид вместе с группами;
- `MySession.EnableCreativeTools`, вызванный на сервере, включает творческие инструменты и самому серверу (локальный
  вызов `OnCreativeToolsEnabled`), и сервер на это время ничего не списывает из инвентарей: сварка без компонентов,
  лишние пластины при разборке. `reg_grid_paste` кладёт игрока в `CreativeTools` напрямую, как это делает его клиент;
- цвет GPS-метки выделенный сервер не сохраняет вовсе: `MyGpsCollection.ChangeColorOnServer` применяет его, только
  если сервер не выделенный; цвет живёт на клиенте и пропадает после перезахода;
- услуги станций (ремонт, утилизация, хранилище гридов) работают только в её безопасной зоне, а урон в зоне запрещён:
  повреждённый корабль проверке нужно сделать до зоны; зона узнаёт о вошедшем гриде не сразу;
- рация костюма работает, пока батарея костюма отдаёт питание (`RadioBroadcaster.Enabled`); выбор игрока —
  `WantsToBeEnabled`;
- в полном прогоне площадки стоят рядом (раньше через 1000 м, теперь через 8 км): проверка, которая забирает себе «новые гриды рядом», должна узнавать
  свои по владельцу, иначе уберёт чужой (голова ротора `reg_subgrid_damage` пропадала в конце `reg_store_buy_ship`);
- контрактов сопровождения (Escort) в этой версии игры нет: в `ContractTypes_Economy.sbc` такого типа нет, и генератор
  отвечает `Error`;
- набор магазинов игроков в экономике пишет `MyStoreBlock.Init` и с рабочих потоков (параллельное создание гридов) —
  ванильная гонка, ломавшая набор и вешавшая игровой поток; сценарий `player_store_race`, исправление — SO
  `PlayersStoreThread`.

## Сценарии

**SentisClusters: отцеплённые кластеры (Detach)**
- `pb_detach` — два корабля в 8 км (два кластера), у каждого программируемый блок, скрипт которого каждый тик
  перебирает блоки, щёлкает светом, гироскопом, тягой, таймером, снимает и ставит головку ротора, перекладывает
  слиток, шлёт сообщение IGC через антенны и считает чужие, сканирует другой корабль камерой. Четыре фазы по 30 с:
  без отцепления, отцеплён A, B, оба (`!clusters detach`). Скрипты всегда идут в игровом потоке, сущности
  отцеплённого кластера - в его. Нужен SentisClusters; не входит в регрессию (переключает отцепление).
- `turret_detach` — нагрузка для Detach: кучи Spitfire (около 43 турелей каждый) по 30 км вдоль X, цели пиратов
  вокруг, по фейковому игроку у каждой кучи и три лёгких кластера. `focus`: `clusters=3 ships=30 targets=20 ammo=1
  hold=400`, а `spacing=100 spin=1 pull=1` сводит корабли и вращает их: грузит физика (турели и сварка дешёвые).
  `python C:\SE\tools\detach_speed.py detach_ms=2 focus="spacing=100 spin=1 pull=1"` - скорости кластеров без
  отцепления и с ним.
- `welder_perf_detach` — установки `welder_perf` в нескольких кластерах (`focus`: `clusters=3 rigs=3`).
- `jump_detach` — прыжки между отцеплёнными и обычными кластерами в обе стороны: станция на площадке (её кластер
  отцеплён), буй в 7 км; корабль прыгает к бую (в обычный), обратно (в отцеплённый), к бую, отцеплённому заранее, и
  обратно в прикреплённую площадку. После каждого прыжка корабль в кластере назначения и идёт на тяге. Нужен
  SentisClusters; не входит в регрессию (отцепляет кластеры).
- `regression_heavy` — регрессия, 90% космических проверок в трёх плотных кучах (`run_regression.py --heavy`).

**Базовые**
- `smoke` — стенд жив: грид спавнится, двигается и удаляется.
- `player_store_race` — 8 раундов по 256 гридов с магазином игрока создаются параллельно (как вставка): набор магазинов
  экономики цел после каждого (без SO `PlayersStoreThread` он ломается с первого раунда, и игровой поток потом виснет
  навсегда). Набор проверяется обходом цепочек с ограничением шагов, сломанный пересобирается.
- `planet_tunnel_mass` — 100 кораблей разом в грунт на 100 м/с; провалившиеся должен вернуть SGI.
- `patch_audit` — ни один перевыпускаемый Torch метод (патчи всех плагинов) не остался с изменённым
  потоком управления из-за ошибки `leave`.
- `patch_retbuf` — ни один перевыпускаемый Torch метод не получает аргументы не на своих местах: метод структуры
  (указатель на структуру копия принимает за объект) или экземплярный метод, возвращающий структуру через скрытый буфер.
- `patch_jumps` — каждый пропатченный Torch метод входит в копию прыжком из одной инструкции (SO `TorchJumpFix`): прыжок
  Torch из двух (`mov rax; jmp rax`) давал CLR неверно раскрутить стек при остановке потока на сборку мусора.
- `patch_params` — у каждого префикса и суффикса Torch и Harmony тип параметра тот же, что у передаваемого аргумента
  (число или структура, принятые за объект, — ссылка, по которой пойдёт сборщик).
- `translator_load` — не даёт ли SentisTranslator фризов: 16 игроков (половина русских, половина английских) и
  нагрузка тяжелее живого чата — 2 сообщения игроков в секунду, 10 строк на экран в секунду с меняющимся числом,
  оповещение в чат всем раз в секунду, строка на экран всем раз в 2 с; одна и та же нагрузка по 45 с с выключенным и с
  включённым переводчиком. Печатает кадры обеих половин и время методов переводчика в игровом потоке (вызовы за кадр,
  мкс за вызов, мс за кадр); падает, если переводчик берёт больше 0,5 мс за кадр. 22.10.2026: 0,025 мс за кадр, кадры
  с ним и без него одинаковые (p99 30,4 и 30,5 мс).
- `patch_conflicts` — ни один метод не пропатчен сразу и Torch, и Harmony: каждый пишет свой переход в начало метода,
  и выполняется только записанный последним. Для каждого такого метода печатает патчи обоих и какой из них работает
  (куда ведёт переход). Нашёл 22.10.2026 десять таких методов: финализаторы SO на репликации, окно сохранения хранилища
  гридов, префикс SEDiscordBridge на падении.
- `reg_grid_storage_save` — грид не убирается в хранилище терминала услуг, пока сохраняется мир (SO
  `GridStorageSaveWindow`): во время сохранения корабль остаётся, записи нет, после — убирается. В общий набор не входит:
  сохранение всего мира посреди набора тормозит соседние проверки.
- `wreck_restore` — восстановление провалившихся гридов SGI по одному на обломках мира «Wrecked Hauler» (двери,
  коннекторы): после исправления порядка выключения тел в `FallInVoxelDetector.MoveGroup` сервер не падает.
- `ground_probe` — реальный грунт (содержимое вокселей, а не сгенерированная поверхность) столбиками в точках
  колёсных площадок: где ямы, пещеры, насколько грунт ниже сгенерированного.
- `terrain_restore` — возвращает к сгенерированному грунт, накопанный сценариями, и колёсные площадки целиком
  (плитками по 100 м, кроме мест у статических гридов). Копающие сценарии (`voxel_stream`, `voxel_cache_resend`,
  `fall_through_tunnel`, `drill_perf`) теперь засыпают за собой сами (`WorldApi.RevertTerrain`).
- `bot_radiation` — бот SentisAi под радиацией пережидает её в своей герметичной кабине, а не умирает. Сценарий
  играет за планету (на Европе 0,6 в секунду всем, кто не в укрытии): начисляет радиацию боту стенда, пока тот
  на ногах. Бот должен сесть в кабину до 74,5, выйти, когда радиация спадёт, и не потерять здоровья. Нужен бот
  на ногах с ровером не дальше 300 м; идёт до 10 минут, в общий прогон не входит.
- `bot_pit` — бот SentisAi без водорода на дне шахты 26 м с камерой внизу (в 25 м от того места, где он стоял)
  должен выйти на поверхность за 6 минут в том же теле. `bot_pit_closed` — то же без шахты: над головой камень, устье
  его ямы в 2 м сбоку (задаётся боту), база в 350 м. `bot_pit_far` — то же без известного устья (как после перезапуска).
  Карманы бота заполняются камнем, чтобы он шёл домой. Грунт после себя возвращают. В общий прогон не входят.
- `bot_cliff` — бот SentisAi с полными карманами и без водорода в 45 м от базы, между ними воронка 20 м шириной и 13 м
  глубиной: должен дойти до базы за 4 минуты, ни разу не быстрее 12 м/с и без потери здоровья. `bot_cliff_h2` — то же
  с половиной бака: падение тормозит джетпак. Грунт возвращают. В общий прогон не входят.
- `bot_seat_finish` — пассажирское кресло на базе бота срезается до 60% (работает), компоненты кладутся в контейнер
  базы: бот должен доварить его полностью за 8 минут. В общий прогон не входит.
- `ai_status_ui` — страница SentisAi для Torch создаётся в своём потоке WPF и трижды спрашивает статус ботов: текст
  должен прийти, сервер — остаться жив (до исправления Torch падал в Havok, как только вкладку открывали).
- `bot_refuel` — бот SentisAi с пустым костюмом заправляется водородом у набора выживания своей базы от
  генератора O2/H2 (набор и генератор соединены конвейерами), без возрождения. Сценарий сам кладёт лёд в
  генератор, если его мало. Нужна такая база на стенде; до 12 минут, в общий прогон не входит.
- `turret_probe` — зонд, не тест: минуту пишет в лог состояние турелей на базах ботов и ставит волка в 30 м от
  заряженной турели: видит ли она его, берёт ли в цель, что стоит на линии огня.
- `fatal_exception` — роняет сервер нарочно необработанным исключением в отдельном потоке: проверка того, что
  `CrashDump` успевает записать полный дамп (`CrashDumps\crash_*.dmp`) до того, как Torch убьёт процесс. Только
  вручную, в общий прогон не входит.
- `struct_this_gc` — пропатченный метод структуры, лежащей полем объекта, переживает непрерывные сборки мусора
  (`MyExplosionInfo.AffectVoxels`: до 29.09.2026 сборщик падал на нём через секунды).

**Сварка и проекции**
- `projector_weld` — строительный корабль ванильными сварщиками строит проекцию 10×10 целиком.
- `mixed_weld` — то же с блоками всех типов; все функциональные блоки должны появиться.
- `frozen_radius_weld` — `projector_weld` после заморозки корабля, смены радиуса во время заморозки и
  разморозки.
- `hand_weld` — два персонажа ручной сваркой строят стену.
- `welder_perf` — шесть сварочных кораблей строят настоящий военный корабль из проекции, замер кадров.
  Чертёж корабля (Spitfire) встроен в плагин, грид в мире не нужен. Варианты:
  - `welder_perf_dynamic` — платформа динамическая, в открытом космосе;
  - `welder_perf_sz`, `welder_perf_sz_dynamic` — то же внутри безопасной зоны с выключенным уроном
    (платформа статичная / динамическая), с пробой зоны;
  - `welder_perf_sz_dynamic_noprobe` — без пробы, только кадры;
  - `welder_perf_sz_dynamic_vanilla` — то же с выключенным `SafeZoneGridTracking` (зона как в игре).

**Безопасные зоны**
- `safezone_border` — гриды поперёк границы зоны и внутри неё, к которым добавляют по блоку за кадр, и
  чужой корабль с ротором, 20 раз влетающий в зону и вылетающий из неё. Проверяет, что зона держит гриды
  после постройки, отпускает закрытые, ловит каждый вход и выход чужого корабля; меряет проверки форм,
  события фантома, блокировки моторов и стоимость отслеживания гридов.
- `safezone_border_vanilla` — то же с выключенным `SafeZoneGridTracking`.
- `safezone_ram`, `safezone_ram_vanilla` — корабль с пилотом на 100 м/с таранит статичную плиту в зоне с
  выключенным уроном (с трекингом плагина / как в игре). Проверяет, что ни плита, ни корабль не повреждены,
  что зона вносит корабль и выносит его после вылета и сообщает об этом клиентам; для контроля тот же
  таран вне зоны должен разбить оба грида.
- `projection_stream` — платформа с проектором доходит до клиентов.

**Производство и фризер**
- `production` — ванильная цепочка руда → завод → конвейер → сборщик.
- `refinery_perf` — 64 грида по 101 заводу, замер кадров переработки. `refinery_perf_busy` — то же, но каждый кадр
  искусственно нагружен на 13 мс перед обновлениями блоков (`Game/FrameLoad.cs`): проверка бюджета кадра SO
  (`ProductionFrameBudget`) — руда вся переработана, в игровых кадрах почти столько же, тиков заводов в разы меньше.
- `freeze_production`, `production_freezer_stress` — компенсация производства замороженных гридов:
  выход точно как у незамороженных.
- `freeze_repeat_disassembly` — то же для разборки в повторе (пластины в выходе сборщика): после разморозки очередь равна
  пластинам, которые остались в сборщике, спавший разобрал не меньше работающего и не больше, чем позволяет рецепт за
  прошедшее время, самый долгий кадр меньше 1 с. Со старым кодом SO на этом сценарии сервер завис (сторож Torch), с
  промежуточным — сборщик выталкивал разбираемое в ящик и вставал с пустой очередью;
- `freeze_repeat_production` — сборщик в режиме повтора у замороженного грида (два грида производства, один спит 3
  минуты, рядом такой же работает): после разморозки спавший собирает столько же пластин (в пределах 5 %), очереди обоих
  остаются как были, самый долгий кадр компенсации меньше 1 с. Раньше компенсация в повторе вешала игровой поток
  (сторож Torch, 21.10.2026);
- `freeze_disassembly` — разборка в сборщике у замороженного грида. Четыре сборщика в режиме разборки: один работает
  рядом с игроком, второй с той же кучей компонентов двигателя спит две минуты, ещё два спят с одним и с двумя
  компьютерами при очереди в тысячу. Проверки: у каждого слитков получено ровно за разобранное; «короткие» разобрали
  всё, что было, и не получили больше; спавший разобрал не меньше работавшего и не больше, чем позволяет время по
  рецепту. До исправления SO (08.10.2026) падал: один компьютер давал слитки за три.
- `freeze_power` — заряд батарей, уран и топливо у замороженных гридов.
- `freezer_physics`, `freezer_stress`, `freezer_stress_profile`, `piston_stack` — заморозка физики
  шасси, колёс, поршней и шарниров: ничего не отрывается, не проваливается и не улетает. В мире без планеты у точки
  `wheel_perf` (копия мира сервера) точка ставится на поверхность самой большой планеты (`WorldApi.PlanetAnchor`), а
  риги `freezer_physics`, построенные у другой планеты, поворачиваются «верхом» вверх и ставятся на грунт: раньше они
  оказывались в 300 км над поверхностью, и разморозка «не случалась» — рядом никого не было.
- `rover_thaw` — 64 копии ровера из мира по 8 планетам, в зонах станций и вне, на ручнике и без; фризер замораживает и
  размораживает их, как при компенсации; каждая разморозка пишется со скоростью и глубиной в грунте. `rover_spawn_probe` —
  почему копии разлетались: каждый кадр скорость, глубина нижней точки в грунте, физика грунта, заморозка тел, шаг мира
  Havok; первый кадр быстрее порога записывается целиком (SO `ThawGuard`: подъём из грунта и обнуление скоростей).
- `thaw_fall`, `thaw_fall_far`, `thaw_fall_nosector`, `thaw_fall_toggle` — гриды, вдавленные в грунт за время заморозки, после разморозки не улетают.
- `jump_freeze` — прыжковые двигатели заряжаются за время заморозки (SO `FrozenProduction`): от реактора — столько же и за
  столько же урана, сколько рядом с игроком; от батарей — сколько дают 32 МВт за это время.
- `/freezer-near` (DebugBridge) — замороженные гриды, у которых ближе дистанции фризера (`static`, `dynamic`, по
  умолчанию 3000 и 10000 м) есть живой персонаж, с ближайшим и расстоянием: то, что должно было разморозиться.
- `physics_resume` — кластер физики, где никого нет, и его возвращение, когда приходит игрок (SO
  `SelectivePhysicsBodies`). Риги с сабгридами на временной планете и в космосе, все в движении: скорость без шага
  не копится, после возвращения нет рывков, ничего не оторвалось. Фризер и очистка мусора на время прогона выключены.
- `client_mod_whitelist` — клиентские моды плагинов (GridPrediction из SGI, мод SentisRender) компилируются компилятором
  модов сервера с белым списком; скрипт, читающий файл, не компилируется (белый список включён). `focus` — своя папка.
- `physics_cluster_timing` — замер кластеров физики (SO `PhysicsCost`: раз в 30 кадров один кластер шагается отдельно
  с секундомером) шагает каждый кластер ровно раз за кадр: два корабля летят по инерции в разных кластерах, путь за кадр
  с замером и без совпадает до 0,3%; кадр с замером дороже меньше чем на 3 мс. Третий прогон — с галочкой SO «Выключить мониторинг физики»:
  ни одного замера, путь тот же.
- `physics_guard` — сторож физики SO с новым счётом: установка из 14 поршней в космосе, пороги ниже её доли
  (`PhysicsCost.Share`), действия над чужими гридами перехватываются; установка становится статикой за минуту.
- `physics_calibration` — сколько физики стоит грид на самом деле: каждый случай один в своём кластере с фейковым
  игроком, кластер замеряется каждый кадр. Кубы, палки, решётки, полые коробки и скосы в космосе (покой, вращение до
  1,8 рад/с, полёт, рядом со станцией), установка на поршнях, два касающихся куба; на планете — покой, падение,
  опрокидывание, лежание, неспящие блок, плиты 3x3 и 5x5, малый грид, куб, плита и палка, куб на статичной плите, вращение в воздухе. Итог по случаю в
  лог, каждый замер с телами, скоростями, касаниями и числом форм — в `physics_calibration.csv` рядом с отчётами.
- `physics_share` — доля шага внутри одного кластера идёт по цене, а не по блокам: куб из 1000 блоков на статичной плите
  (дёшево) и палка из 152, упавшая на грунт (дорого), у одного игрока; палке достаётся больше чем вдвое.
- `physics_mechanisms` — как `physics_calibration`, для механизмов: стек поршней стоя и на ходу, ротор пустой и с плитой
  на 30 и 5 об/мин (в космосе), ровер на стоянке и на ходу, поршень, вдавливающий головку в грунт (на планете).
  Рядом с каждым замером — то, что предсказывает `PhysicsCost`, в `physics_mechanisms.csv`.
- `physics_sticks` — палки из брони на планете: 1×20…1×500 стоя и лёжа (не спят), 1×500, 2×125 и 5×20, заваливающиеся из
  вертикали. Тяжёлый: палка 1×500, лежащая на холмах, стоит до сотен мс за шаг — стенд всё время прогона тормозит.
- `physics_explain` — пять самых дорогих групп мира по `PhysicsCost.Share` (и грид `Cedar` с фейковым игроком рядом;
  другой грид — полем `focus` вызова `test` у DebugBridge, например `{'name': 'physics_explain', 'focus': 'Бур Физика'}`):
  по гридам — формы, касания, цена; тела блоков; пристыкованное; кластер и другие группы в нём.
- `physics_neighbours` — грид `Cedar` и группы в 300 м от него копиями на пустых ровных местах той же планеты (та же
  высота над грунтом и наклон), у каждой свой игрок: что каждая стоит одна. Копии удаляются.
- `physics_ship_probe` — настоящий корабль мира (`Shokaku` или грид из `focus`, иначе самый большой динамический): на месте с игроком рядом
  (спит ли, что в кластере), затем копии со всем пристыкованным в пустом космосе, неспящие — целиком, по гридам,
  одна броня, уснувшая броня: замер кластера против пустого и то, что даёт `PhysicsCost`. Программируемые блоки
  копий выключены, копии удаляются.
- `physics_tools` — сколько стоят инструменты против того, что кладёт на грид `PhysicsCost`: каждый случай один в своём
  кластере с фейковым игроком, кластер замеряется каждый кадр. Буровой корабль стенда (`Resources/PhysicsDrillShip.xml`,
  «Бур Физика» из сейва, 159 блоков, 8 буров) в пустом космосе, у своего астероида `Asteroid256-001` в 5 м от камня,
  прижатый к нему с выключенными бурами, копающий на 0,5 м/с, в вырезанном туннеле; астероид один; динамическая плита
  7x5 с десятью сварщиками строит из своей же проекции стену из 30 блоков брони снова и снова (готовая стена сносится),
  то же без проекции; то же сварщиками на отдельном гриде, лежащем на плите. Итог по случаю — замер сверх пустого
  кластера, доля по `PhysicsCost`, касания, формы.
- `physics_drill_live` — настоящий буровой корабль мира («Бур Физика» или грид из `focus`) бурит свой настоящий
  астероид: корабль ставится в метре от камня перед бурами (камня нет — разворачивается к ближайшему астероиду), игрок
  в 60 м, по кругу шесть раз по 8 секунд: стоит, бурит (буры включены, корабль толкается вдоль них на 0,5 м/с), стоит.
  По каждому состоянию: шаг физики, доля корабля по `PhysicsCost.Share`, его кластер в одиночку и что он добавляет к
  шагу (обычный шаг минус остальные кластеры в кадре замера). Руда из инвентарей корабля перед прогоном высыпается,
  корабль остаётся там, куда добурил.
- `unstepped_blocks` — там, где кластер не шагает, коннекторы не ищут пару и сенсор не смотрит (SO
  `SelectivePhysicsBodies`); пришёл игрок — через доли секунды кластер шагает, сенсор его видит, коннекторы сцепляются.
- `power_switch` — энергия грида следует за переключателями (SO `DistributorUpdate`): батарея, лампа, блок достроен и срезан.
- `panel_server` — у экрана программируемого блока на сервере применяется текст от модов и уходят клиентам
  нарисованные спрайты (SO `ServerGridRender` пропускает остальную отрисовку панелей).
- `fall_through_tunnel` — возврат провалившихся гридов (SGI `AutoRestoreFromVoxel`) не трогает то, что стоит
  под землёй нарочно. Плита в пещере под каменной полкой остаётся на месте, зарытая плита поднимается. Голова
  ротора статичного грида, зарытая в скалу, не двигается, и статичный грид тоже.
- `laser_link_awake`, `laser_control_anchors`, `remote_control_anchors` — замороженный корабль
  доступен через лазерную антенну и дистанционное управление.
- `pb_save_thread` — при сохранении мира `Save()` скрипта программируемого блока незамороженного грида вызывается
  в игровом потоке (SO `ParallelEntitySave`). На старой сборке он шёл на рабочем потоке, это причина падений старого
  сервера 28–29.09.2026.
- `pb_save_frozen` — у замороженного грида `Save()` скрипта, в котором есть код, при сохранении мира вызывается
  в игровом потоке, а гриды со скриптами с пустым `Save()` или без него собираются на рабочих потоках
  (SO `ScriptSaveCode`). Проверяет и то, как плагин читает скрипты, скомпилированные игрой.
- `voxel_blocking_probe` — проба, а не проверка: 5 минут без фризера записывает, кто заставляет Havok строить
  воксельную сетку посреди запроса и какие лучи из очереди шага физики (`CastRayParallel`: ветряки, солнечные панели,
  турели) идут дольше 1 мс - чьи они, сколько сетки построено внутри, сколько лучей ждало рядом. Итог строкой
  `VOXEL BLOCKING RESULT`, медленные лучи - `SLOW PHYSICS QUERY`. В общий прогон не входит.
- `bot_no_duplicate` — бот, у которого блок сети базы (генератор O2/H2, базовый сборщик или печь) перестал работать,
  доваривает его и не строит второй такой же: сценарий срезает блок до нерабочего и 20 минут следит за базой.
  Нужен бот, который находится у своей базы или может до неё добраться.
- `bot_spare_block` — бот спиливает лишний блок базы: сценарий ставит на базу второй генератор O2/H2 (или базовый
  сборщик, или печь) от имени бота и до 15 минут ждёт, пока блок этого вида снова останется один. Базу, где лишний
  блок уже есть, наблюдает как есть.
- `bot_move_apart` — бот возвращает на конвейеры блок, стоящий отдельно: сценарий переносит единственный генератор
  O2/H2 (или базовый сборщик, или печь) базы на её крышу, в стороне от сети, и до 25 минут ждёт, пока блок этого вида
  (один, рабочий) снова будет достижим по конвейерам от набора выживания — через конвейерные блоки или после
  спиливания и установки заново. Второй такой же блок на базе — провал.
- `top_grids_players` — держатель для замера, а не проверка: ставит по фейковому игроку с персонажем (неуязвимым и
  невидимым для турелей) у 20 самых тяжёлых гридов мира и держит их 7 минут при включённом фризере. Гриды берутся по
  именам из `Instance\SentisTests\top_grids.txt` (пишется из таблицы `load` Watcher), недостающие добираются по числу
  блоков. Нагрузку в это время снимает `tools/burst.py`. В общий прогон не входит.
- `frozen_save_perf`, `save_perf` — сохранение мира: снимок гридов и заранее собранные снимки
  замороженных.

**Производительность блоков**
- `drill_perf` — 32 корабля по 36 буров.
- `grinder_perf` — 400 резаков.
- `gas_perf` — 400 генераторов O2/H2.
- `thrust_ion`, `thrust_atmo` — двигатели под нагрузкой.
- `pb_perf` — тяжёлые программные блоки и их наказание.
- `tool_offset` — сдвиг рабочей сферы сварщика вперёд (SGI `WelderForwardOffset`): большой сварщик среди каркасов;
  при 0 он варит и каркасы по бокам от носа, при 1,8 м и при 2 м, выставленных на лету, — только впереди; сфера стоит
  ровно на сдвиг дальше, поиск проекций SO (`GetWelderSphereShift`) сдвинут так же.
- `rotor_place`, `rotor_place_freezer`, `rotor_spawn`, `rotor_fix`, `rotor_fix_off`, `piston_head_guard` — головки
  роторов и поршней, поставленных игроком (`BuildBlocksRequest` и `RequestGridSpawn` от клиента): каркасом на базе и на
  корабле, отдельным гридом на земле и в воздухе, головка из терминала, фиксшип SGI с недостроенными и достроенными
  основами, переподключение клиента со сверкой отданных клиенту билдеров, заморозка и разморозка фризером. Головка
  должна быть прицеплена, со связью в физике, на месте и не наклонена. `rotor_fix` сбивает головки сразу после
  установки — проверка SO (`MechanicalTopCheck`) их возвращает; `rotor_fix_off` то же с выключенной проверкой (головки
  остаются сбитыми). `piston_head_guard` — «Добавить головку» поршня, у которого проверка падает: без исключения.
  `rotor_place_zone`/`rotor_place_zone_game` — то же в зоне безопасности с белым списком. `rotor_audit` и `rotor_live` —
  пробы мира с сервера: все роторы мира сейчас и роторы, которые ставит живой игрок, покадрово.
  `rotor_place_preloaded` — то же, но модели стадий голов сначала загружены фоновым потоком SO, как при начале резки
  грида: до 12.10.2026 они выходили из него без коллизии, головы-каркасы получали коллизию целым кубом и сползали со
  статора.
- `construction_model_shapes` — модели стадий стройки, загруженные заранее фоновым потоком SO (`GrinderPatches`),
  с коллизией их файла; поршень без головки получает её через «Add Top», как у ботов.
- `assembler_pull_probe` — проба мира: сколько стоит фризеру SO поиск ресурсов сборщика в других блоках грида
  (`FreezerPatches`), по сборщикам крупнейших гридов; печатает сумму найденного, чтобы сравнить сборки.
- `rig_shake` — почему трясётся буровая бота (живая, у «База Cedar»): самый быстрый грид буровой и размах плеча при
  ней как есть, с остановленным ротором, с остановленным лифтом, с выключенными бурами, с общим тензором инерции, с
  наибольшими импульсами поршней. Всё возвращается как было.
- `drill_print_probe` — шасси бота и проекция летающего бура в нём: что изучено, лимиты, батареи, какие блоки можно
  варить; пишет ячейки бура от магнитной лапы шасси в `Instance\DrillCells.txt` (из них — `Blueprints/DrillCells.txt`
  SentisAi) и проверяет тест «порода» (куб под лапой — да, над ней — нет).
- `drill_dock` — пилот SentisAi (`GridPilot`) ведёт бур из чертежа ботов к большому коннектору тестовой базы за
  стеной и стыкует его; с фейковым игроком рядом (иначе фризер). PASSED — коннекторы соединены.
- `drill_dock_line` — где бот SentisAi ставит коннектор базы для летающего бура, когда сверху на базе места нет: база из
  трёх конвейеров под «крышей» из брони (другой грид) 13×13 в 10 м над ней. Боту на время его поиска (вызов за кадр)
  подставляется эта база; поиск должен найти линию конвейеров от порта к месту вне крыши, ни один вызов на игровом
  потоке не дольше 100 мс. Потом база пересоздаётся с построенной линией — коннектор должен встать на её конец.
- `drill_mine` — то же, что `drill_dock`, с копкой по дороге (режим пилота `MineFirst`): в 30 м по другую сторону
  от коннектора бур поворачивает нос (буры) на 60° вниз, идёт в грунт, пока ход не встал (корпус шире бурового торца)
  или трюм не заполнен наполовину, выходит задним ходом, выравнивается и стыкуется. PASSED — пристыкован и привёз
  больше 50 кг (на стенде 72 т камня за 187 с).
- `bot_drill_fly` — живой Cedar сам: копия бура «от его имени» рядом с ним, бот садится в кокпит, летит к коннектору
  своей базы и стыкуется (копия потом убирается). Нужен коннектор на базе.
- `drill_state` — летающий бур бота как он есть (только чтение): коннектор, шасси, двигатели, батареи, чего касается
  корпус. Бур ищется по имени («Атмосферный бур …»).
- `ai_task_split` — блок задачи ИИ, отвалившийся от грида в бою, потом удалённый; бой выключается и включается снова.
  Без SO `AiTaskBlockLeftGrid` — NullReferenceException в `MyAiBlockSystem.DeactivateComponent` (падение прода 14.10.2026).
- `component_list_race` — один `MyComponentList` заполняется в одном потоке и очищается в другом, как предпросмотр
  проектора и снятие проекции. Без SO `ComponentListLock` словарь зацикливается, и поток виснет навсегда (до
  перезапуска сервера).
- `gas_weld_refresh` — каркас 100×50×200 больших блоков с вентиляцией и закрытой комнатой, 40 с сварки (блок
  ставится недоваренным и доваривается): сколько раз газовая система пересчитывала комнаты, доля времени, что она занята
  в рабочем потоке, и сколько длится пересчёт (SO `GasRoomRefresh`). Проваливается, если комната с вентиляцией не
  загерметизировалась, когда закрыли стену, или внешний воздух не совпал с ванильной заливкой.
- `docked_door` — дверь на динамическом гриде, сцеплённом коннекторами со статичным: закрыть, открыть, закрыть. Створки
  должны быть в группе столкновений грида, тела створок — там, где створки, дверь — доходить куда сказано (SO
  `DockedCollisions`).
- `door_probe` — только чтение: двери рядом с настоящими игроками (состояние, тело грида, тела и фильтры створок,
  связи) и сейфзоны вокруг.
- `ownership_missing_block` — смена владельца с блоком, которого у сервера нет (последним в списке): без SO
  `OwnershipRequestCheck` игра выходит за конец списка и выкидывает игрока.
- `piston_projection` — поршни из проекции, как их строит сварщик SO (`MyProjectorBase.Build`), с диагностикой
  `PistonTopPlacement`.
- `conveyor_reach` — «довезёт ли конвейер» (`CanTransferItemTo`, `IsConnectedTo`) с SO `ConveyorReach` против
  ванильного поиска: все пары инвентарей крупнейших сетей мира; тестовая база с односторонним сортировщиком (фильтр,
  выключен, без питания, блок чужой, расшарен, срезан конвейер) и сцепленный коннектор мира (расцеплен, сцеплен,
  торговля) — каждое изменение спрашивается в том же кадре, в следующем и после паузы, с ожидаемым ответом.
- `docked_shake`, `docked_shake_off`, `connector_shake` — гриды, сцеплённые коннекторами: тряска и отбрасывание при
  расцепке с исправлениями SO и без них; `connector_shake` — замер пары «Бур»/«Опорник Бурмалда» из копии мира прода
  (имя грида — `ConnectorShakeScenario.GridName`).
- `pb_static_init` — скрипты со статической инициализацией, скомпилированные вне игрового потока (SO `PbCompile`):
  класс со статическим конструктором (минимальный скрипт из PR #2 и `Settings` из AutomaticSystemBase), инициализатор
  поля с объектами скрипта, инициализатор, читающий статику класса с конструктором, `Program` со `static readonly`
  полями. Каждый должен отработать без исключения и после перекомпиляции. До PR #2 падал с
  `TypeInitializationException`; число подготовленных методов каждого скрипта — в логе при `Diagnostic logs` SO.
- `piston_perf`, `piston_extend` — поршни в мире.
- `character_perf` — персонажи на джетпаках.
- `wheel_perf`, `wheel_perf_64`, `wheel_small*`, `wheel_parked_64`, `wheel_physics_ab` — колёсная техника.
- `wheel_fall*`, `wheel_restore*` — провал колёсной техники сквозь грунт и её возврат.
- `gear_probe` — в какую сторону защёлкивается шасси.
- `thrust_flame` — пламя двигателя жжёт броню только при тяге и на полную длину; десятикадровое обновление двигателя выключается.
- `turret_target` — турель без целей вокруг берёт в цель игрока, подошедшего на 60 м.
- `turret_wolves` — турель на батарее прямо на земле, вокруг четыре порождённых сценарием волка в 20–46 м с разных
  сторон: турель поворачивается от одного к другому и убивает всех, не стреляя мимо (ствол не дальше 25° от цели).
- `turret_wolf` — живой волк мира переносится в 30 м от самой высокой турели базы бота, турели даются магазины её
  типа; проходит, только если волка убила турель. `turret_wolf_idle` — то же с включённым вращением в простое.
  Сейчас падает: под турелью на 10-блочной мачте волк ниже 45° закрыт верхним блоком мачты.
- `turret_watch` — зонд, не тест: 15 минут смотрит на турели баз ботов как есть — в кого стреляют, что на линии огня,
  теряет ли цель здоровье; пустой турели со зверем в радиусе кладёт пять её магазинов.
- `pb_iim` — чертёж игрока с Isy's Inventory Manager (путь в `IimBlueprintPath`, в репозитории его нет;
  без пути или файла сценарий `SKIPPED`) вставляется статичным гридом с выключенным ПБ, ПБ включается как игроком; наказание SentisOptimisations включено. Три
  минуты пишет каждый замер PBFix (первые запуски, все дольше 2 мс с задачей скрипта), самый долгий кадр после вставки и
  после включения, и сгорел ли блок. В конце билдер грида собирается на рабочем потоке, ПБ должен остаться включённым.
  Наказание срабатывает только после 3 минут работы сервера. `pb_iim_watch` — то же без наказания.
- `pb_save_offthread` — ПБ со скриптом с `Save()` в гриде, вставленном из билдера: скрипт сам запускается, билдер грида
  дважды собирается на рабочем потоке (как параллельное сохранение замороженного грида), ПБ не выключается.

**Сеть**
- `replication_perf`, `replication_alloc` — 64 клиента, 64 завода и летающие корабли: репликация, мусор,
  время подключения.
- `voxel_stream` — подключение возле раскопанной планеты не останавливает сервер.
- `asteroid_resend`, `grid_resend` — астероид из префаба (или грид из 9 блоков) в пустом космосе, фейковый клиент в
  200 м, первая загрузка у клиента «не удаётся» (`FakeClients.FailLoad`: клиент выбрасывает поток и ничего не отвечает,
  как настоящий). Объект должен стать готовым у клиента за 75 с (грид — 105 с) (SO `ReplicableResend`).
- `grid_stream` — подключение возле огромного грида.

**Игровые механики (SentisGameplayImprovements)**
- `explosions` — взрывы боеголовки и взрывчатки на плите брони, лут.
- `asteroid_field` — поле астероидов `!sgi spawnfield`/`spawnfield2`: место свободно, руды только заданные, общий цикл плагина не блокируется.
- `voxel_stuck` — застрявший в вокселях грид: в космосе переносится на 1 км в свободное место, сабгрид статичной базы и грид в гравитации становятся статикой.
- `explosion_friendly_fire` — взрыв не задевает свой грид при выключенном дружественном огне мира.
- `warhead_chain`, `warhead_mass_chain`, `warhead_mass_all` — цепные реакции и тысяча боеголовок разом.
- `cockpit_eject` — пилот уничтоженного кокпита выживает с 3% здоровья, пилот уцелевшего не задет.
- `loot_jumpdrive` — лут уничтоженного прыжкового двигателя считается один раз.
- `gravity_drive` — гравидвигатель не двигает корабль.
- `contract_prices` — множители наград контрактов: каждый игровой метод награды на работающем сервере при
  множителе 1 и 7.5.
- `pcu_limit` — лимит PCU: корабль сверх лимита (блоки выключены, на пятой проверке подряд статика),
  корабль в лимите, NPC-корабль, база с ротором (статичный лимит), сброс счёта после возврата в лимит.
  Проходы лимитера по миру на время сценария остановлены: он проверяет только свои гриды.
- `world_sweeps` — проходы плагинов по миру на гридах сценария: маяк контрабанды (учёт в радиусе, забывание
  ушедшего, цена прохода против старого при 2000 гридах), запоминание сканов фризера, выключение блоков без
  владельца и переименование, множитель резака по кадрам.
- `pcu_limit_cost` — цена лимита PCU для игрового потока: 20 копий Spitfire, проверка группы, перебор её
  блоков и проход по миру по вызовам; заодно проверяет, что счётчик PCU игры не меньше нашего ни у одного грида.
- `pve_zone` — PvE-зона: удары по блоку грида в зоне и вне её от чужого грида, персонажа, взрыва без
  владельца, своего грида, NPC (с `EnableDamageFromNPC` и без), контейнер `Container MK-`, грид, только что
  перенесённый в зону, выключенная зона; настоящие буры (чужой, свой, чужой вне зоны) и таран на 100 м/с;
  урон по персонажу в зоне от чужого грида, персонажа, корабля, взрыва без владельца, NPC, своего взрыва,
  удара о землю и вне зоны.

**SentisClusters (обновления кластеров физики в разных потоках)**
- `cluster_twins_production`, `cluster_twins_weld`, `cluster_twins_chain`, `cluster_twins_warheads` - несколько копий
  сценария (`production`, `projector_weld`, `warhead_chain`, `warhead_mass_chain`) одновременно, в 150 км друг от
  друга - каждая в своём кластере физики. Каждая копия должна пройти, как проходит одна, и все - примерно за одно
  время: гонка между потоками кластеров видна как копия, потерявшая работу, бросившая или не закончившая.
  Замеряется кадр за весь прогон.
- `cluster_twins_toggle` - копии `production`, пока параллельный режим SentisClusters включается и выключается каждые
  3 с: переключение посреди работы ничего не должно потерять.
- `top_grids_players_open` - как `top_grids_players`, но без требования фризера и с удержанием 25 минут: держатель
  для внешних замеров «с кластерами и без».

**Другие плагины**
- `garage_roundtrip` — VirtualGarage: грид в гараж и обратно целым, без пересоздания, без дублей.
- `translator_chat` — SentisTranslator, модель (llama-server) переводит по-настоящему. Четыре фейковых игрока: A и D читают по-русски, B и C по-английски; сообщения идут через чат-конвейер Torch (`ChatManagerServer.RaiseMessageRecieved`), что шлёт плагин, перехватывается по игрокам:
  - глобальный чат: русское — перевод B и C, английское — A и D, автору ничего;
  - `!st off` / `!st on`: ответ только автору, переводы ему выключаются и включаются; `!status`, `!stats`, `!stuck` — не `!st`;
  - команды, «ok», одна ссылка, сообщение самого сервера — ничего;
  - язык, на котором игрок пишет, становится его языком;
  - чат фракции — перевод членам фракции, кому нужен; личный — адресату;
  - встроенный режим — сообщение задержано, B и C получают «текст (перевод)», D оригинал сразу;
  - `!st help` — окно со списком команд (клиентский мод Torch) и строка в чат, без админских команд для не-админа;
  - `!st lang ru` — выбранный язык не меняется от сообщений, `!st lang auto` — снова определяется; `!st setlang` от не-админа — отказ;
  - Discord (заглушка SEDiscordBridge, `Scenarios/DiscordBridgeStandIn.cs`: класс с тем же именем, вызывает тот же `SendMessageAsOther`): общий канал — перевод всем, кому нужен, под «[t] автор »»; канал фракции — тому, кому сообщение пришло, модель переводит один раз;
  - `!st disable` от не-админа — отказ.
  Настройки плагина меняются в памяти и возвращаются; реальные игроки онлайн на время сценария считаются отписавшимися.
- `translator_restart` — SentisTranslator: процесс llama-server убит (как при падении), плагин сам поднимает его, и чат снова переводится.
- `join_leave_burst` — 20 игроков разом входят, разом выходят (персонажи остаются) и разом возвращаются, 3 раза: худший

- `floating_objects_limit` — сверх лимита мира (`MaxFloatingObjects`) выброшено ещё 30 пластин: за 15 с в мире не больше
  лимита. Только отдельно: лишними убираются самые старые объекты, в том числе чужие.
- `translator_say`, `translator_say_inline`, `translator_say_discord` — посмотреть перевод в игре самому: фейковый игрок пишет в общий чат текст из `focus` (`api('test', {'name': 'translator_say', 'focus': '...'})`), сообщение уходит как от игрока; `_inline` — встроенный режим на одно сообщение (в памяти), `_discord` — «сообщение из Discord» от «[D] John» через заглушку бриджа, в лог — что плагин отправил и кому. - `watcher_record` — SentisWatcher: позиции игрока и грида, перенос предметов (запрос от клиента игрока), урон, содержимое инвентаря и «кто был рядом» записаны и читаются командами; честный перенос не даёт алерта о дюпе.
- `watcher_load` — SentisWatcher под нагрузкой: 64 Spitfire с игроками в кокпитах летают туда-сюда, двое прыгают; окна с записью и без сравнивают цену кадра, потом проверяется, что позиции, инвентари, захват управления и прыжки записаны и ничего не потеряно.
- `watcher_ledger` — учёт инвентарей SentisWatcher: честные перенос, сборка и переработка, разборка прототех-гироскопа в лом и починка корабля ALE ShipFixer с пилотом на прожекторе (блоки и пилот загружаются заново) не дают алертов; сборка и разборка без входа, переработка без руды и правка стака в обход игры дают свои алерты; учёт игрока раскладывает каждое изменение по источнику (в том числе «плагин SentisTests» и «необъяснено»).
- `npc_spawn` — SentisAdventures:

  - база на планете стоит вертикально, статично, низом на грунте, без блоков в скале.

- `chat_reach` — для каждого игрока онлайн: находит ли Torch его личность по Steam id и подключён ли клиент (сообщение

## Запуск на сервере

1. `SentisTests` (dll, `0Harmony.dll`, `manifest.xml`, `LICENSE`, `NOTICE`) — в `Plugins\SentisTests`,
   сервер перезапустить. Конфиг `Instance\SentisTests.cfg` Torch создаст сам; образец —
   [`SentisTests.cfg.example`](SentisTests.cfg.example).
2. `!test list` — что можно проверить на этом сервере. `!test run all` — прогнать всё по порядку,
   `!test status` — что идёт сейчас и сколько в очереди. Можно через DebugBridge: `POST /test`.
3. Результат в логе Torch (`Logs\Torch-<дата>.log`): `[TEST] PASSED`/`FAILED`/`SKIPPED`, итоговая строка
   сценария и замеры; отчёты — в `Instance\SentisTests\`.

Сценарии строят в мире корабли, руду, заводы и планету-риг, передвигают и удаляют гриды. Нужен тестовый
мир с запасом ресурсов и без ценного; после прогона мир обычно не сохраняется. Часть сценариев длится
десятки минут (`bot_*`, `watcher_load`), `run all` на полном наборе — несколько часов.
